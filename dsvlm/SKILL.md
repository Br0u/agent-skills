# DSVLM 视频算法编排

把用户的自然语言视频识别需求，转换成华鲲元启 AI 平台 `视频解析 -> 策略中心 -> 算法配置` 的可填写配置。

不要把这当成普通 prompt 编写。页面有固定组件，先判断组件，再写条件；没有明确提交授权时只输出方案。

## 快速入口

| 请求形态 | 行为 | 写入 |
| --- | --- | --- |
| `/dsvlm 评审：人员落水` | 场景探索或方案评审 | 否 |
| `/dsvlm 新建：识别垃圾车；算法名：垃圾车识别` | 生成新算法配置表 | 否 |
| `/dsvlm 新建：识别垃圾车；算法名：垃圾车识别；主题：园区A --post` | 按主题名匹配 ID 后提交新算法 | `POST /s/theme/data` |
| `/dsvlm 优化：识别火情；问题：排除灯光误报；主题：园区A` | 读取该主题的现有算法并输出替换方案 | 否 |
| `/dsvlm 优化：识别火情；问题：排除灯光误报；主题：园区A --post` | 合并修改并保存原算法 | `PUT /s/theme/data` |
| `python3 scripts/algorithm_service.py --list / --add ...` | 读取或新增 9079 语义算法 | 视参数而定 |

## 安全边界

- 只有原始用户请求里有独立 `--post` 才能写平台；不要推断用户想提交。
- `评审` 永远不上传，即使同一句里出现 `--post` 也只做分析。
- 只有用户明确要求保存时，才点击 `确定` 或运行写入脚本。
- `主题：...` 是用户自定义值，不固定为 `wbr`。DSVLM 会去掉首尾空格后按名称区分大小写精确匹配 `themeTypeId`。
- 主题未找到、存在多个不同 ID、目录鉴权失败，或名称匹配结果与显式 ID 不一致时，立即停止列表读取、优化查找和提交。
- 不读取 `DSVLM_THEME_TYPE_ID`，也不使用内置默认主题；同名算法只在本次匹配到的主题内查重或复用。
- 同名算法只能在本次已确定的主题内查重或复用；其他主题的同名算法不算复用。
- 9079 当前使用明文 HTTP；仅在确认目标主机和当前网络可信后，才可在已忽略的私有 `.env` 中一次性设置 `DSVLM_SERVICE_ALLOW_INSECURE_HTTP=true`；`.env.example` 继续保持 `false`。
- 8898 直登携带管理员账号密码；明文 HTTP 默认拒绝。只在确认目标主机和网络可信后，才可在私有 `.env` 设置 `DSVLM_ALLOW_INSECURE_HTTP=true`；不要修改 `.env.example` 的 `false`。
- 需求有歧义、模块不确定、英文标签不确定、业务逻辑不确定或是否保存不确定时，先问。
- 不要把 Authorization、Cookie、access token 写进 README、references、提交记录或回复正文。

## 请求解析

- 动作只接受 `新建：`、`评审：`、`优化：`。
- 字段用中文或英文分号分隔：`算法名：`、`问题：`、`主题：`、可选 `补充：`。
- `--post` 是唯一保留的用户旗标，必须独立放在请求末尾。
- `--loop`、`--save`、`--update`、`--d:` 已移除，不提供兼容解析。
- `新建` 不提交时可省略主题；`优化` 和所有真实提交必须填写主题。

## 页面字段

路径：`视频解析 -> 策略中心 -> 算法配置 -> 新增/修改`

| 字段 | 说明 |
| --- | --- |
| `算法` | 算法名称 |
| `思维条件 N` | 组件和填写内容 |
| `解析模式` | 通用、深度、深度串行 |
| `预警等级` | 一级到五级：一级最严重，五级为仅检测 |
| `启用区域框` | 是否只检测画面指定区域 |
| `排序` | 默认自动 |
| `添加到门户` | 用户指定或重点展示类算法才开 |
| `对接编码` | 用户指定才填 |
| `备注` | 简短说明 |

预警等级按业务风险选择：一级为最严重，二级为重大违规，三级为一般违规，四级为轻微违规，五级为仅检测/身份或场景监测。

## 新增算法流程

1. 判断任务类型：对象、属性、动作、状态、关系、缺失、文字，还是复杂场景。
2. 把抽象标签拆成摄像头可见证据，不要直接写 `违规`、`异常`、`贴广告`。
3. 先找可见锚点：人、车、门、手、纸张、刀、棍、头盔、水域、护栏、表情、服饰等；默认用 `目标理解 / 多模态目标理解`，目标标签写英文，例如 `person`、`car`、`underage people`。多模态目标理解通常比正/反向语义思维更适合先找明显目标，含状态的目标也可放在第一条。只有用户指定或已有实测证明更稳时，才改用 `通用目标理解`。
4. 再写语义复核：手是否拉门、骑手是否未戴头盔、人是否持械/推搡/翻越、车辆是否载人等，用 `内容理解` 或 `深度内容理解` 判断动作、关系和状态；细动作或高误报行为可同时用普通正向思维和正向深度思维双校验。
5. 反向排除默认放在主证据之后；高误报场景可前置窄反向排除作为过滤门槛，但只排除明确正常或画面不可判定的情况，例如看不到头、看不清脸、正常交谈、制服工作人员持刀具。
6. 判断逻辑：共同成立用默认 AND；任一独立分支成立才加 `逻辑理解 / 或者`，并把每个分支完整展开。
7. 场景风险类任务先写真实场景门槛，再写最强、最可见的危险判据；场景门槛不稳时，可用 `深度内容理解 / 正向深度思维1` 补一条。
8. 选解析模式：简单锚点可用 `通用模式`，整图事件和复杂语义用 `深度解析模式`，多锚点局部交互可用 `深度串行解析`。
9. 输出固定字段：`算法`、`解析模式`、`预警等级`、`启用区域框`、`排序`、`思维条件`、`备注`。
10. 做生成前自检，再回复用户。

## 参数调优路径

已有正例、反例或平台实测结果时，按“先参数、后提示词”的顺序调优，避免一开始把语义规则越写越复杂：

1. 先用平台的目标理解验证功能检查目标标签、阈值和远近比，再确认目标框大小是否合理。
2. 优先调整 `阈值`、`远近比`、`延伸比例`、`解析模式`；仍有明确误报或漏报时，再改提示词、使用分屏检测、反向思维或深度内容理解。
3. 提示词调优可尝试同义目标词、给业务词补可见定义、用少量相近词复核；只有出现幻觉或结果不稳定时，才对同一概念做正向/反向确认。
4. 大场景中寻找小特征（横幅、裸露上身、老鼠、生产线小物体等）时，优先考虑平台分屏检测；不要靠堆长提示词弥补目标过小。
5. 全量解析和自定义描述适合抽样、打标或观察模型描述，资源消耗较大；普通检测任务不要默认开启。每次调优都要在目标部署场景的正例和反例上复核，因为画质、干扰项和参数会共同影响结果。

## 修改已有算法流程

触发格式：

```text
/dsvlm 优化：识别火情；问题：排除灯光误报；主题：园区A
```

处理流程：

1. 用用户填写的主题名精确匹配 `themeTypeId`，再只读该主题列表：`python3 scripts/post_theme_config.py --theme-data-page --theme-name '园区A' --theme-label '算法名'`。
2. 找不到同名算法时，直接说明未找到；不要凭空重建成“已有算法”。
3. 找到后，用算法 `id` 读详情：`python3 scripts/post_theme_config.py --theme-data-detail 'id'`。
4. 以详情为原版本，只改用户指出的误报、漏报或新增约束；误报优先追加或改写反向排除，不要整套重写。
5. 没有独立 `--post` 时只给替换方案；有独立 `--post` 时，把最终配置转成 JSON 后用 `--payload - --user-request '原始请求'` 提交，脚本从请求的 `主题：...` 解析 ID。
6. update 模式保存时走 `PUT /s/theme/data`，脚本会查同名算法、读取旧详情、只替换输出表里的字段，不新建同名算法。

示例：`/dsvlm 优化：识别火情；问题：灯光总是误测为火情；主题：园区A`。先匹配园区A并读取 `识别火情`，再补充排除稳定灯光、车灯、反光、暖色照明；不要推倒原有火焰、烟雾等主证据。

## 评审流程

触发 `/dsvlm 评审：xx` 时，读取 `references/loop-strategy.md`。

- 只做场景探索、方案完整性检查和优劣评审，不生成上传 payload，不调用提交脚本。
- 默认做输入判定、证据探索和方案收敛；无新增、重复或主要变成不可验证假设时停止。
- 只回复评审结果，不自动创建本地文件。
- 输出是候选编排分析或方案评审，不是最终可提交算法。

## 组件选择

| 场景 | 默认选择 |
| --- | --- |
| 只找具体物体 | `目标理解 / 多模态目标理解`，锚点标签优先英文 |
| 物体加状态、属性、关系 | 先用英文 `多模态目标理解` 锚定，再用 `内容理解` 或 `深度内容理解` |
| 动作、状态、关系、一般语义 | `内容理解` |
| 身份、年龄、服饰、细节状态、复杂上下文 | 先用英文 `多模态目标理解` 锚定，例如 `underage people`，再用 `深度内容理解` 复核 |
| 文字/OCR | `文字理解 / OCR` |
| 未佩戴、缺失、看不到 | 先找主体和场景，再用目标缺失或反向思维排除不可判定画面 |
| 持械、暴力、翻越、拉拽 | 先锚定人和关键物/部位，再用内容或深度内容确认危险动作 |
| 细动作、高误报交互 | 目标锚定后，用 `正向思维` + `正向深度思维` 做双语义复核 |
| 任一独立正向候选成立就预警 | `逻辑理解 / 或者`，且每个 OR 分支都完整展开 |
| 已有模板、截图或平台配置明确给出 | 可用 `全结构化理解`；不要主动发明 |

组件细节、字段格式和 `parsingId` 映射见 `references/platform-components.md`。

## 核心规则

### 条件和逻辑

- 思维条件按从上到下的顺序逐层过滤；上方条件不满足时，不会继续执行下方条件。
- 不添加任何 `逻辑理解` 行时，平台会把思维条件默认按 AND 组合。
- 默认 AND 不是要求所有编排都必须 AND；先判断业务逻辑。
- `逻辑理解 / 或者` 按编程语言里的 `||` 理解：它分隔完整分支，不是局部连接上一条和下一条。
- 公共前提和公共排除项不会自动跨 OR 继承；需要在每个分支里重复写。
- 例如 `A && B && (C || F) && !D && !E` 要展开为 `A && B && C && !D && !E || A && B && F && !D && !E`。
- 同一条语义里的枚举，例如“短裙、低胸上衣、超短裙任一”，优先写在同一个内容理解条件里，不要滥用平台 OR。
- OR 常用于“不同目标锚点代表同一风险”的分支枚举，例如 `paper in hand` 或 `card` 都代表小广告材料，`knife` 或 `stick` 都代表持械攻击，`truck carrying people` 或 `tricycle/bicycle carrying people` 都代表违规载人；每个分支都要重新写目标和动作。
- 不要用 `A 或者 反向排除B` 表达“排除 B”；OR 会把反向条件变成独立分支，逻辑上可能让配置失效。
- `正向思维1` 是原始 prompt 能力，填写内容基本就是最终 prompt。
- `正向思维2` 是调优迭代版，内部已有固定提示词，填写内容会作为变量传入。

### 目标和区域

- `目标理解` 必须分别填写数量和显式 `阈值 N`；不要把两者混为一项。
- 只有 `目标理解 / 通用目标理解` 或 `目标理解 / 多模态目标理解` 检测出的物体才会套框。
- 内容理解、深度内容理解本身不会给物体套框。
- 找锚点默认用英文 `多模态目标理解`，包括平台内置目标也优先写英文多模态，例如 `person`、`car`、`dog`、`hand`、`car door`、`helmet`、`stick`、`underage people`；只有用户指定或已有实测证明更稳时，才用 `通用目标理解`。
- `启用区域框` 表示只检测画面中的指定区域，不是使用整个画幅作为检测范围。只有一个区域框时通常留空设备区域编码，且绘制区域不要命名；若任一思维条件填写了区域编码，其他思维条件也要填写，整图编码使用 `full`。
- 远近比用于按目标框在画面中的相对大小过滤检测结果；低于最小值或高于最大值的目标框会被过滤。它是目标大小的筛选参数，不等同于真实物理距离，也不扩展目标上下文。
- 延伸比例用于扩大深度解析或深度串行解析中的锚点目标区域；后续条件只在目标框及延伸区域内处理。比例过小可能丢失眼镜、手部、车门等局部上下文，过大可能引入相邻目标；整图事件不要强依赖延伸比例。
- 阈值不是固定 50。教程给出的起始经验是常见人/车约 70-80、少见目标约 35-40，但必须用目标理解验证功能按当前场景校准。全画面找人/车时可设置远近比最小值过滤远端小目标并节省算力；不要把这些经验值当成固定默认。
- 有明确目标框、需要定位告警对象时开 `启用区域框`；纯整图分类、不需要框或目标框不稳定时可关。
- `添加到门户` 不默认开启；只有用户要求、重点展示类算法或需要门户侧直接查看时再开。
- 直接事件或身份标签稳定时可以单条 `多模态目标理解` 起步，例如 `person in water`、`underage people`、`Hazardous Chemical`、`crowd gathering`；但涉及行为成因或误报高的任务仍要补语义复核。
- `排序` 用户未指定时填 `自动`；post 时脚本会读取原有算法列表，并排到当前最大排序之后。

### 建模偏好

- 初始配置优先用 2-4 条稳定主证据跑通，不要默认添加反向排除。
- 条件描述优先“短描述 + 强判据 + 少量排除”：每条只抓一个最关键、摄像头可见的判断点，避免长句堆叠太多细节把语义组件变成硬门槛。
- 有实测反例时，先检查阈值、远近比、延伸比例和解析模式，再修改提示词或增加反向条件；不要用复杂 prompt 掩盖目标框或裁剪范围错误。
- 反向思维主要用于调试误报；误报优化按“先补场景门槛，再补朝向/互动关系，最后补误报排除”的顺序。
- 小物体、细线、局部变化、远景低清结果不要默认作为硬条件。
- 对“小物体 + 人手动作”任务，不要只识别小物体；至少补一条手部持有、拉拽、张贴、挥舞、递交等动作确认。
- 对拉车门、手持刀棍、拉横幅、翻越栏杆、未戴头盔等局部交互，不要只停在目标锚点；用普通正向思维确认动作，再用正向深度思维复核细节和关系。
- 多目标关系不要只写 `人 AND 车`；必须补关系或动作条件。
- 判断物体安装、悬挂、粘贴、摆放状态时，先用 `目标理解` 锚定物体，再用内容理解写位置关系和安装方式。
- 缺失、未穿戴类任务先找大目标，再用反向思维排除明确合规状态。
- 未佩戴类任务不要只写 `helmet = 0`、`口罩 = 0`；先确认骑手/人员和对应头脸部位可见，再判断未佩戴，并排除看不到头、看不清脸等不可判定画面。
- 暴力、持械、跌倒、冲撞等风险任务优先写正向危险动作，例如推搡、拉扯、挥拳、踢踹、持刀攻击、持棍攻击、肢体撕扯冲突；反向只排除正常交谈、搭肩、握手、姿态放松、制服工作人员等窄场景。
- 服饰、表情、奇装异服等细节任务，先用目标标签锚定，再用深度语义确认“与周围明显不符、脸部可见、表情夸张”等可见差异；看不清、遮挡、戴口罩时不要硬判。
- 车辆载人、翻越栏杆、拉横幅、交通事故等事件类任务，优先用事件目标标签或主体目标锚定，再用内容理解复核事件是否真的发生，不要停在 `人 + 车/栏杆/横幅` 的并列目标。
- 存在多个独立危险来源时才用 OR，例如 `跌倒冲突`、`持刀攻击`、`持棍攻击` 三类分别成立；每个分支都要包含本分支的目标和正向行为。
- 临水、禁区、道路、工地等风险类任务，先限定真实场景，例如河流/水域/工地/道路，再判断人员面部、身体或视线是否朝向危险源，避免正常路过、背对休息、远处背景水面等误报。
- 临水防溺水不要只写“有人在水域边缘”；优先抓攀爬、跨越、骑跨护栏、手脚搭栏杆、身体探出等人与水域边缘的高危交互动作，再用反向思维排除正常走路、散步、骑行、钓鱼等非危险活动。
- OR 分支里的公共场景门槛和反向排除都要重复写。

## 解析模式

| 模式 | 用法 |
| --- | --- |
| `通用模式` | 简单锚点、普通物体识别、目标关系容易被串行拆散时使用 |
| `深度解析模式` | 有一个多模态目标锚点时，后续判断只基于该目标框及延伸区域；适合目标细节、行为语义、身份服饰、脸部表情、事故状态；需要全图关系时不要强行裁剪 |
| `深度串行解析` | 有两个或以上多模态目标理解时，后一个目标只在前一个目标框及延伸区域内继续识别；适合多锚点局部交互、穿戴缺失、手部动作、目标间逐步过滤 |

选择规则：

- 不要机械默认 `通用模式`。简单物体可用通用；截图式复杂策略里，深度解析和深度串行解析经常更合适。
- 例如“人是否戴眼镜”可在深度串行解析中先识别 `person`，再只在该人的目标框及延伸区域内识别 `glasses`；不要把这一局部范围规则套用到通用模式。
- 需要给物体套框时，必须包含 `目标理解` 组件。
- 两个及以上 `目标理解` 不等于必须用 `深度串行解析`；如果是整图事件或关系，先考虑 `深度解析模式`。
- `人 + 狗`、`人 + 车` 这类整图关系判断，串行解析可能拆散目标关系，不要强行串行。

## 提交脚本

`scripts/post_theme_config.py` 默认只预览；stdin JSON 只负责传配置，只有原始 `--user-request` 里有独立 `--post` 才写入。

常用命令：

```bash
python3 scripts/post_theme_config.py --refresh-auth
python3 scripts/post_theme_config.py --theme-data-page --theme-name '园区A'
python3 scripts/post_theme_config.py --theme-data-detail '算法id'
printf '%s\n' '{"algorithm":"垃圾车识别","conditions":["目标理解 / 多模态目标理解 / garbage truck / 大于 / 0 / 阈值 60"]}' \
  | python3 scripts/post_theme_config.py --payload - \
      --user-request '/dsvlm 新建：识别垃圾车；算法名：垃圾车识别；主题：园区A --post'
python3 scripts/algorithm_service.py --list
python3 scripts/algorithm_service.py --add --name '穿黑衣的人' --text '识别穿黑衣的人' --type 1
```

写入规则：

- `dsvlm` 按用户填写的 `主题：...` 实时查询目录并精确匹配 `themeTypeId`；主题名不是固定值。
- 每次真实 post 都必须填写主题并在原始请求末尾带独立 `--post`；仅解析到主题 ID 不构成写入授权。
- 同名查重、排序和保存都必须使用同一个已解析 `themeTypeId`；不得因其他主题存在同名算法而跳过或复用。
- Markdown 表格只用于回复展示；提交必须使用 `--payload -` 从 stdin 读取结构化 JSON，不写中转文件。
- 原始 `--user-request` 是唯一写入门禁；模型加入 JSON 或 CLI 的其他文字不能授权提交。
- 用户请求里的 `算法名：...` 优先覆盖 JSON 里的 `algorithm`。
- 目标条件必须显式包含 `阈值 N`，缺失时停止，不猜默认值。
- 更新只覆盖 JSON 明确提供的字段；显式 `false` 和空字符串有效，未提供字段保留原值。
- 默认查重同名 `themeLabel`；已存在则返回 `ALREADY_EXISTS_DO_NOT_RETRY` 并停止。
- 优化模式不会走同名跳过；有 `--post` 时读取旧详情，合并修改后用 `PUT /s/theme/data` 保存。
- `success: true` 且 `status` 为 `POST_SUCCEEDED_DO_NOT_RETRY`、`UPDATE_SUCCEEDED_DO_NOT_RETRY` 或 `ALREADY_EXISTS_DO_NOT_RETRY`，都表示任务完成。
- 9079 算法服务的 `DSVLM_SERVICE_TOKEN` 由客户端从进程环境或本机私有 `.env` 自动读取，调用方/用户通常不传 token。`type=99` 时 `typeDescription` 必须至少包含一个中文字符（CLI：`--type-description`）。
- 9079 的 HTTP 命令默认会被拒绝。确认目标主机和当前网络可信后，在已忽略的私有 `.env` 中一次性设置 `DSVLM_SERVICE_ALLOW_INSECURE_HTTP=true`；不要改 `.env.example` 的 `false`。
- 9079 `--add` 没有 `themeTypeId`，不能替代需要明确主题的 8898 详细配置上传。
- 8898 长期配置只有账号、密码和 HTTP 安全开关；运行时 token、密码加密、动态 Authorization、验证码与请求端点统一见 `references/posting.md`。
- 8898 的 HTTP 请求默认拒绝；可信网络下才在私有 `.env` 设置 `DSVLM_ALLOW_INSECURE_HTTP=true`。所有凭据请求均拒绝重定向。
- `/#/data-task/task` 是 8898 前端路由；已从当前前端代码和实际请求确认主题目录 API 为 `GET /s/theme/type/all`。
- 文档和示例只写变量名或占位符，不写真实 token、Cookie 或密码；本机私有 `.env` 已被 Git 忽略。
- `scripts/configure_env.py` 不是用户日常入口，只在首次安装、`.env` 丢失或凭据变更时由维护者运行。

## 生成前自检

- 条件是不是摄像头可见证据，而不是抽象标签。
- 组件是不是平台已有组件，没有发明新选项。
- 锚点目标是否默认用了英文 `多模态目标理解`，而不是中文抽象词或机械使用 `通用目标理解`；例如未成年人应优先写 `underage people`。
- 更新模式是否确实读取到同名现有算法，而不是只按算法名猜配置。
- 更新模式是否只改和新需求直接相关的最少条件。
- 多条件默认 AND 是否符合业务；任一独立分支成立才加 `逻辑理解 / 或者`。
- 是否把 `逻辑理解 / 或者` 两侧分支完整展开；公共前提、公共排除项是否已在每个分支重复。
- 是否错误地把 `逻辑理解 / 或者` 和反向思维混用成独立预警分支。
- 场景风险类任务是否先限定真实场景，并判断人员与危险源的朝向或互动关系。
- 条件描述是否足够短，是否只保留最强可见判据；有没有把多个细节堆进一条条件导致漏报。
- 是否已经区分“可见锚点、语义复核、反向排除”，而不是只堆目标标签。
- 细动作或高误报交互是否用了普通正向思维和正向深度思维双校验。
- 未佩戴、看不到、表情、脸部类任务是否确认关键部位可见；不可判定画面是否被窄排除。
- 持械、暴力、事故、翻越、拉横幅、载人等事件类任务是否补了真实动作或事件复核。
- 解析模式是否匹配任务：简单物体、整图事件、多锚点局部交互不要混用。
- 阈值、远近比、启用区域框、添加到门户是否有业务理由，还是机械照抄。
- 是否先按“阈值 -> 远近比 -> 延伸比例 -> 解析模式 -> 提示词/分屏/反向/深度”的顺序处理已知反例。
- 需要大场景小目标时，是否考虑分屏检测；是否误把资源消耗较大的全量解析当成日常检测开关。
- 临水防溺水是否从“靠近水域”收紧到“攀爬、跨越、骑跨、探身”等高危动作，并排除正常经过、散步、骑行、钓鱼。
- `目标理解` 是否同时写了数量和显式阈值，并且没有混淆两者。
- 是否只有在用户指定或已有实测证明更稳时，才使用 `通用目标理解`。
- 原始用户请求没有独立 `--post` 时，是否没有触发提交。
- 真实 `--post` 是否填写主题；主题名是否已唯一解析；缺失、无匹配或歧义时是否已停止。

## 硬约束

- 不要编造用户未提供、页面未见过的模块选项。
- 不要把置信度当成目标数量。
- 不要把抽象行为直接当作最终条件。
- 不要默认添加反向排除；先根据误报类型追加。
- 不要机械默认通用、深度解析或深度串行解析；按任务结构选择。
- 不要在用户未明确授权时保存配置。
- 不要在真实 post 时默认信任 `.env` 或内置的主题 ID。
