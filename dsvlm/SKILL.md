# DSVLM 视频算法编排

把用户的自然语言视频识别需求，转换成华鲲元启 AI 平台 `视频解析 -> 策略中心 -> 算法配置` 的可填写配置。

不要把这当成普通 prompt 编写。页面有固定组件，先判断组件，再写条件。

## 入口命令

| 用户请求 | 行为 |
| --- | --- |
| `/dsvlm --config` | 弹出新终端窗口，粘贴三段 cURL 自动配置 `.env` |
| `场景：xx场景 --算法名` | 只生成方案或 dry-run |
| `场景：xx场景 --算法名 --post` | 明确授权提交 |

入口规则：

- 用户请求是 `/dsvlm --config`、`--config` 或明确说配置鉴权时，只处理 `.env` 配置，不生成算法方案。
- 配置鉴权时，打开新窗口运行 `scripts/configure_env_from_curl.command`。
- 配置窗口会依次提示粘贴 `auto-login-url`、`login`、`theme data page` 三段 DevTools `Copy as cURL`，自动写入 `.env`。
- 新窗口打开后，告诉用户在窗口完成三轮粘贴，再回到当前 agent 继续问答。
- `post_theme_config.py --config payload.json --post` 只表示用 JSON payload 提交，和 `/dsvlm --config` 不是同一个入口。

请求解析：

- `场景：` 后到第一个 `--` 前是场景需求。
- 第一个 `--` 后是算法名，例如 `--垃圾车识别`。
- 只有末尾出现独立的 `--post` 才提交；不写 `--post` 就只 dry-run。
- 旧格式 `--算法名称：垃圾车识别` 仍可作为算法名兜底，但默认优先用 `--算法名` 短格式。
- `场景：流浪猫狗 测猫狗` 是旧两段格式，不是新格式：不得提交，也不要把 `测猫狗` 当成算法名。
- 用户原话是 `场景：流浪猫狗 --测猫狗` 时，只生成方案或 dry-run；只有 `场景：流浪猫狗 --测猫狗 --post` 才提交。

## 安全边界

- 没有看到原始用户请求里独立的 `--post`，绝不提交。
- 不要推断用户想 post。
- 只有用户明确要求保存时，才点击 `确定` 或运行写入脚本。
- 需求有歧义、模块不确定、英文标签不确定、业务逻辑不确定或是否保存不确定时，先问。
- 不要保存 Authorization、Cookie、access token 到 README、references 或回复正文。

## 页面字段

路径：

```text
视频解析 -> 策略中心 -> 算法配置 -> 新增/修改
```

主要字段：

| 字段 | 说明 |
| --- | --- |
| `算法` | 算法名称 |
| `思维条件 N` | 组件和填写内容 |
| `解析模式` | 通用、深度、深度串行 |
| `预警等级` | 一级、二级、三级预警 |
| `启用区域框` | 是否只检测画面指定区域 |
| `排序` | 默认自动 |
| `对接编码` | 用户指定才填 |
| `备注` | 简短说明 |

## 生成流程

1. 判断任务类型：对象、属性、动作、状态、关系、缺失、文字，还是复杂场景。
2. 把抽象标签拆成摄像头可见证据，不要直接写 `违规`、`异常`、`贴广告`。
3. 选组件：具体物体用 `目标理解`；动作、状态、关系用 `内容理解` 或 `深度内容理解`。
4. 判断逻辑：共同成立用默认 AND；任一成立才加 `逻辑理解 / 或者`。
5. 选解析模式：默认 `通用模式`；不要因为“深度”听起来更强就默认用深度或串行。
6. 输出字段：`算法`、`解析模式`、`预警等级`、`启用区域框`、`排序`、`思维条件`、`备注`。
7. 自检后再回复用户。

生成前自检：

- 条件是不是摄像头可见证据，而不是抽象标签。
- 组件是不是平台已有组件，没有发明新选项。
- 多条件默认 AND 是否符合业务；任一成立才加 `逻辑理解 / 或者`。
- `目标理解` 数字是不是置信度，不是目标数量。
- 原始用户请求没有独立 `--post` 时，是否没有触发提交。

| 算法 | ... |

| 预警等级 | ... |

```

| 提交字段 | 结果 |

| 平台说明 | ... |
```

没有要求 `--post` 时，不输出提交结果表。

## 组件选择

快速决策：

- 只找物体：`目标理解`。
- 物体加状态、属性、关系：先 `目标理解` 锚定，再用 `内容理解` 或 `深度内容理解` 判断。
- 动作、状态、关系、复杂语义：默认 `内容理解`。
- 身份、年龄、服饰、细节状态：优先 `深度内容理解`。
- 缺失、未穿戴：先找大目标，再用反向思维排除明确合规状态。
- 任一候选成立就预警：加 `逻辑理解 / 或者`。

| 组件 | 适用场景 | 默认建议 |
| --- | --- | --- |
| `内容理解` | 动作、状态、关系、一般语义描述 | 默认优先 |
| `深度内容理解` | 身份、年龄、服饰、细节状态、复杂上下文 | 需要细节判断时使用 |
| `目标理解` | 具体物体识别 | 物体类优先 |
| `文字理解 / OCR` | 文字/OCR 需求 | 只在文字类需求中使用 |
| `逻辑理解` | 条件块之间的 OR 关系 | 只做逻辑连接 |
| `全结构化理解-深度` | 已有模板、截图或平台配置明确给出 | 不主动发明 |

组件细节见 `references/platform-components.md`。

## 核心规则

条件和逻辑：

- 思维条件按从上到下的顺序逐层过滤；上方条件不满足时，不会继续执行下方条件。
- 不添加任何 `逻辑理解` 行时，平台会把思维条件默认按 AND 组合。
- 默认 AND 不是要求所有编排都必须 AND；先判断业务逻辑。
- 任一候选成立就预警时，显式添加 `逻辑理解 / 或者`。
- `正向思维1` 是原始 prompt 能力，填写内容基本就是最终 prompt。
- `正向思维2` 是调优迭代版，内部已有固定提示词，填写内容会作为变量传入。

目标和区域：

- `目标理解` 最后的数字是置信度，不是目标数量。
- 只有使用 `目标理解 / 通用目标理解` 或 `目标理解 / 多模态目标理解` 时，检测出的物体才会套框。
- 内容理解、深度内容理解本身不会给物体套框。
- 多模态目标字段尽量写英文，除非已验证平台支持中文。
- `启用区域框` 表示只检测画面中的指定区域，不是使用整个画幅作为检测范围。
- `排序` 用户未指定时填 `自动`；post 时脚本会读取原有算法列表，并排到当前最大排序之后。

建模偏好：

- 反向思维主要用于调试误报；初始配置优先用 2-4 条稳定主证据跑通。
- 小物体、细线、局部变化、远景低清结果不要默认作为硬条件。
- 多目标关系不要只写 `人 AND 车`；必须补关系或动作条件。
- 判断物体安装、悬挂、粘贴、摆放状态时，先用 `目标理解` 锚定物体，再用内容理解写位置关系和安装方式。
- 缺失类任务先找大目标，再用反向思维排除明确合规状态。

## 解析模式

| 模式 | 用法 |
| --- | --- |
| `通用模式` | 默认/普通模式 |
| `深度解析模式` | 深度解析；只有目标理解组件检测出的物体会套框 |
| `深度串行解析` | 多个目标理解部分时可尝试，实测效果不稳定 |

选择规则：

- 默认 `通用模式`。
- 需要给物体套框时，必须包含 `目标理解` 组件。
- 需要身份年龄服饰、细节状态判断时，再考虑 `深度解析模式`。
- 两个及以上 `目标理解` 不等于必须用 `深度串行解析`。
- `人 + 狗`、`人 + 车` 这类整图关系判断，串行解析可能拆散目标关系，先用通用模式。

## parsingId 映射

不要把思维条件行号当作 `parsingId`。脚本会按组件拆成平台真实值。

| 输出组件 | 平台 parsingId |
| --- | --- |
| `目标理解 / 通用目标理解` | `counter` |
| `目标理解 / 多模态目标理解` | `dmt_counter` |
| `内容理解 / 正向思维1` | `1` |
| `内容理解 / 正向思维2` | `11` |
| `内容理解 / 正向思维20` | `21` |
| `内容理解 / 反向思维1` | `2` |
| `内容理解 / 反向思维2` | `12` |
| `内容理解 / 反向思维20` | `22` |
| `深度内容理解 / 正向深度思维1` | `101` |
| `深度内容理解 / 正向深度思维2` | `103` |
| `深度内容理解 / 正向深度思维20` | `121` |
| `深度内容理解 / 反向深度思维1` | `102` |
| `深度内容理解 / 反向深度思维2` | `104` |
| `深度内容理解 / 反向深度思维20` | `122` |
| `文字理解 / OCR` | `ocr` |
| `逻辑理解 / 或者` | `logic_or` |

示例：

```text
思维条件1: 目标理解 / 通用目标理解 / 人 / 大于 / 80
思维条件2: 目标理解 / 多模态目标理解 / garbage bin / 大于 / 80
思维条件3: 内容理解 / 正向思维1 / 出现明火
思维条件4: 逻辑理解 / 或者
思维条件5: 内容理解 / 正向思维1 / 出现浓烟
思维条件6: 文字理解 / OCR / 1
```

## 脚本和提交

`scripts/post_theme_config.py` 默认只预览，只有明确授权才写入。

常用命令：

```bash
open scripts/configure_env_from_curl.command
python3 scripts/post_theme_config.py --auto-login
python3 scripts/post_theme_config.py --refresh-auth
python3 scripts/post_theme_config.py --theme-data-page
printf '%s\n' "$AGENT_OUTPUT" \
  | python3 scripts/post_theme_config.py \
      --agent-output - \
      --user-request '/dsvlm 场景：识别垃圾车 --垃圾车识别'
printf '%s\n' "$AGENT_OUTPUT" \
  | python3 scripts/post_theme_config.py \
      --agent-output - \
      --user-request '/dsvlm 场景：识别垃圾车 --垃圾车识别 --post'
python3 scripts/post_theme_config.py --config payload.json --post
```

写入判定：

- `--theme-data-page` 和真实 post 会优先复用现有 token，探活失败才刷新一次；通常不需要手动 `--refresh-auth`。
- 默认 post 必须使用 `--agent-output -` 从 stdin 读取 agent 刚生成的最终表格；不要先写 `output.txt`。
- 只有用户特别要求调试、复现或留档时，才使用 `--agent-output output.txt`。
- `--agent-output` 以原始 `--user-request` 为准；模型自己乱加 CLI `--post` 不会提交。
- `--agent-output` 会读取输出文本，提取字段并构造 payload。
- 用户请求里的 `--算法名` 或 `--算法名称：...` 优先覆盖输出里的 `算法:`。
- 默认查重同名 `themeLabel`；已存在则返回 `ALREADY_EXISTS_DO_NOT_RETRY` 并停止。
- `success: true` 且 `status` 为 `POST_SUCCEEDED_DO_NOT_RETRY` 或 `ALREADY_EXISTS_DO_NOT_RETRY`，都表示任务完成。
- 写入前先 dry-run 或用 `--theme-data-page` 验证链路。
- 用户未要求 `--post` 时，最终回复不要输出提交结果、提交状态或 dry-run 状态。
- 鉴权、`.env`、动态 Authorization 见 `references/posting.md`。

## 硬约束

- 不要编造用户未提供、页面未见过的模块选项。
- 不要把置信度当成目标数量。
- 不要把抽象行为直接当作最终条件。
- 不要默认添加反向排除；先根据误报类型追加。
- 不要默认使用深度解析或深度串行解析。
- 不要在用户未明确授权时保存配置。
