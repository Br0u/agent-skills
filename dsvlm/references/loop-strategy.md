# Loop 策略

用于 `/dsvlm 场景：xx场景 --loop`。目标不是单纯扩展更多场景，而是做“场景探索 + 方案验证”：既能把模糊需求拆成候选规则，也能检查现阶段方案是否完整、稳健、值得提交。不上传平台。

## 边界

- `--loop` 永远不上传，不输出提交结果表，不运行 `post_theme_config.py`。
- `--loop` 输出的是候选编排分析或方案评审，不是最终可提交算法。
- `--save` 有才保存，没有就只输出。
- 保存路径：`loop_outputs/YYYYMMDD-HHMMSS-场景名-loop.md`。
- 保存文件只写 loop 分析正文，不写 Authorization、Cookie、access token。
- 即使用户同时写了 `--post`，只要请求包含 `--loop`，仍然不上传。

## 轮数

- 默认 2 轮。
- 支持 `--loop N`，N 为正整数。
- 也支持在 `--loop` 后空一行单独写正整数。
- 未指定轮数时按 2 轮处理。
- 不设硬性最大轮数；用户显式指定更高轮数时可以继续脑补。
- 每轮必须有新增价值；无新增、重复或主要变成不可验证假设时提前停止。

## 输入模式

先判断当前请求属于哪种模式：

| 模式 | 输入特征 | 目的 |
| --- | --- | --- |
| 探索模式 | 只有场景名、一句话、缺少正例/反例 | 补齐风险行为、正常行为、可见证据和未知边界 |
| 评审模式 | 已有推荐初版、思维条件、客户正反例或调优描述 | 验证当前方案完整性、优劣、误报/漏报风险 |

如果输入已经足够明确，不要强行扩展；进入评审模式，检查方案是否可直接生成或是否需要补充边界。

## Loop 0：输入判定

输出：

- 输入模式：探索/评审。
- 已知信息：客户已给出的场景、正例、反例、约束、已有条件。
- 缺失信息：影响误报、漏报或能否提交的业务边界。
- 当前结论：可直接生成、需要补充、或只适合先出候选初版。

## Loop 1：探索或还原

探索模式：把场景拆成摄像头可见内容。

| 类别 | 要写什么 |
| --- | --- |
| 风险行为 | 会触发预警的动作、状态、关系 |
| 正常行为 | 不应触发的常见行为 |
| 可见对象 | 人、车、动物、物品、区域、设施 |
| 地点/区域 | 桥边、河岸、道路、门口、工位等 |
| 不可见项 | 动机、身份、授权关系、意图等不可直接判断内容 |
| 未知边界 | 需要客户确认的业务规则 |

要求：

- 只写摄像头能看到的证据。
- 不把“违规”“异常”“危险”当最终条件。
- 不默认引入小物体、细线、局部变化这类不稳定证据。

评审模式：把现有方案还原成意图和证据链。

| 类别 | 要写什么 |
| --- | --- |
| 当前目标 | 这个方案到底想识别什么 |
| 主证据 | 当前条件依赖哪些可见证据 |
| 触发路径 | AND/OR/前置过滤关系是否合理 |
| 排除逻辑 | 哪些正常行为被排除，是否过强 |
| 组件选择 | 目标理解、内容理解、深度内容理解是否合适 |
| 脆弱点 | 哪些条件容易受远景、遮挡、低清、视角影响 |

## Loop 2：收敛或打分

探索模式：把扩展结果收敛成初版可编排条件。

- 保留 2-4 条稳定主证据。
- 优先正向证据，反向思维只用于明显误报排除。
- 默认 `通用模式`。
- 具体物体用 `目标理解`；动作、状态、关系用 `内容理解` 或 `深度内容理解`。
- 任一独立分支成立就预警时，才加 `逻辑理解 / 或者`；加 OR 就把每个分支完整展开，公共前提和排除项在每个分支重复。
- 删除客户没说、摄像头看不到、平台组件不稳定的假设。

评审模式：给当前方案做优劣判断。

| 维度 | 判断标准 |
| --- | --- |
| 完整性 | 是否覆盖核心正例、明确正常反例、关键地点/区域 |
| 可见性 | 每个条件是否能被摄像头直接看到 |
| 稳定性 | 是否依赖小目标、细节、低清下不稳定证据 |
| 误报风险 | 正常行为是否会被触发 |
| 漏报风险 | 典型风险行为是否未覆盖 |
| 简洁性 | 是否能用 2-4 条主证据表达，是否过度复杂 |
| 组件合理性 | 是否用了平台已有且适合的组件 |
| OR 正确性 | OR 是否像 `||` 一样分支化；是否错误依赖跨分支继承 |
| 提交就绪度 | 是否适合生成正式配置，还是需要客户确认 |

评分只用三档：

- `通过`：可进入普通 `/dsvlm 场景：... --算法名` 生成。
- `需小改`：列出最少修改点。
- `需确认`：边界不清，不建议直接生成或提交。

## Loop 3：边界检查和改进建议

第 3 轮及以后用于继续脑补边界，但每轮必须说明新增价值：

- 列可能误报。
- 列可能漏报。
- 列最少修改建议。
- 列必须问客户的问题。
- 标记哪些条件不能在客户确认前写进最终算法。
- 说明本轮相比上一轮新增了什么；没有新增就停止。

不要把第 3 轮及以后的假设自动变成最终思维条件。

## 停止条件

满足任一条件就停止：

- 连续一轮没有新增有效可见证据。
- 新增内容主要是客户没说的业务边界。
- 已形成 2-4 条稳定主证据。
- 误报/漏报检查没有新发现。
- 新增内容只能作为客户确认问题，不能进入算法条件。
- 输出开始重复前几轮结论。

停止时明确写出停止原因。

## 未来接入正常流程

普通生成流程可以在输出前轻量调用 loop 思路，但不要默认输出完整 loop 记录：

1. 先用 Loop 0 判断输入是否足够清晰。
2. 如果清晰，正常生成配置，只做内部自检。
3. 如果模糊但风险低，输出推荐初版并列出假设。
4. 如果模糊且影响提交安全，即使用户写了 `--post` 也先问，不提交。
5. 如果用户显式写 `--loop`，才输出完整 loop 分析。

## 保存规则

如果用户带 `--save`：

1. 创建 `loop_outputs/`。
2. 文件名使用当前时间和场景名：`YYYYMMDD-HHMMSS-场景名-loop.md`。
3. 场景名只保留中文、英文、数字、短横线和下划线；其他字符替换为短横线。
4. 保存内容必须和回复里的 loop 分析一致。
5. 最终回复里追加保存路径。

如果没有 `--save`，不要创建文件。
