# 平台组件和字段

## 目录

- `内容理解`: 正向/反向思维组件和 parsingId
- `深度内容理解`: 深度思维组件和 parsingId
- `目标理解`: 通用目标、多模态目标、套框规则
- `文字理解`: OCR 组件
- `逻辑理解`: OR 和其他逻辑控制项
- `全结构化理解`: 全结构化组件
- `执行顺序`: 条件逐层过滤
- `启用区域框`: 检测区域含义
- `添加到门户`: 门户展示开关
- `解析模式补充`: 延伸比例控件
- `调优辅助组件`: 参数校准、逻辑调试和全结构化外挂过滤

## 内容理解

常用组件：

```text
正向思维1
正向思维2
正向思维20
反向思维1
反向思维2
反向思维20
```

用法：

- `正向思维`：要识别、要出现、要满足的内容。
- `正向思维1`：初版能力；填写内容就是完整 prompt，平台基本按输入内容直接理解。
- `正向思维2`：调优迭代版；内部已有固定提示词，填写内容作为变量传入。
- `反向思维`：主要用于调试误报。不要默认添加；先用正向主证据跑，确认某类误报反复出现后，再针对性补一条。

已从提交 curl 确认的 `parsingId`：

| 组件 | parsingId |
| --- | --- |
| 正向思维1 | 1 |
| 正向思维2 | 11 |
| 正向思维20 | 21 |
| 反向思维1 | 2 |
| 反向思维2 | 12 |
| 反向思维20 | 22 |

选择建议：

- 默认先用 `正向思维1`。
- 当同类需求已经验证 `正向思维2` 更稳，或需要平台内置调优提示词参与判断时，再用 `正向思维2`。
- 不要在同一编排里无理由混用 `正向思维1` 和 `正向思维2`。
- 细动作或高误报交互可以有理由地做双校验：先用普通正向思维确认动作，再用正向深度思维复核细节和关系。

示例：

```text
算法: 识别小女孩
思维条件1: 内容理解 / 正向思维1 / 女孩
思维条件2: 内容理解 / 正向思维1 / 小孩
思维条件3: 内容理解 / 反向思维1 / 成年男人
```

## 目标理解

用于识别具体物体，分两类：

```text
通用目标理解
多模态目标理解
```

只有加了 `目标理解` 下面的组件，平台才会在检测出来的画面里给物体套框。`内容理解`、`深度内容理解` 可以判断语义、状态、关系，但不会单独给物体套框。

### 通用目标理解

不是默认选择。只有用户指定、平台模板已经固定，或已有实测证明比多模态目标更稳时使用。已从平台下拉框确认的通用目标包括：

```text
人
机动车辆
汽车
卡车
摩托车/电动车
公交车
火车
船
红绿灯
狗
猫
手包
行李箱
背包
屏幕
笔记本电脑
椅子
键盘
电话
盆栽植物
瓶子
杯子
碗
床
伞
香蕉
```

默认仍优先用英文 `多模态目标理解`；不要因为目标在内置列表里，就机械改成 `通用目标理解`。

格式：

```text
目标理解 / 通用目标理解 / [内置目标] / 大于|小于|等于 / [数量] / 阈值 [置信度百分比]
```

最后的数字是置信度，不是目标数量。

### 多模态目标理解

默认目标组件。找锚点默认写英文，除非已验证平台支持该中文标签。

```text
人 -> person
未成年人 -> underage people
成年人 -> adults
老人 -> elderly people
汽车 -> car
狗 -> dog
垃圾桶 -> garbage bin / garbage bins
安全帽 -> helmet
叉车 -> forklift
烟雾 -> smoke
车门 -> car door
手 -> hand
棍棒 -> stick
持刀 -> knife / holding bladed weapon
```

格式：

```text
目标理解 / 多模态目标理解 / garbage bins / 大于 / 0 / 阈值 50
```

除非已验证平台支持中文，否则多模态目标字段不要写中文。

身份、年龄、服饰这类目标可先用英文多模态短语锚定，再用内容理解或深度内容理解复核。例如“未成年人检测”优先写：

```text
目标理解 / 多模态目标理解 / underage people / 大于 / 0 / 阈值 50
深度内容理解 / 正向深度思维1 / 画面中人员是否具备明显未成年人特征
```

阈值不是固定 50。教程给出的起始经验是常见人/车约 70-80、少见目标约 35-40，但必须通过平台目标理解验证功能按现场画质校准。全画面找人/车时可设置远近比最小值过滤远端小目标并节省算力；卡车被小外卖箱误识别时可提高远近比最小值，整画面被识别成横幅时可降低远近比最大值。上述数值只是起始经验，不是默认常量。

## 文字理解

只在需求明确是可见文字时使用：

```text
识别屏幕上的“故障”
识别标牌文字
识别车牌/编号
识别告警文字
```

已知平台值：

```text
文字理解 / OCR -> parsingId: ocr
```

格式：

```text
文字理解 / OCR / [要识别的文字或规则]
```

如果平台规则值是固定开关，可直接按页面值填写，例如：

```text
思维条件1: 文字理解 / OCR / 1
```

如果 OCR 需求也能被语义理解覆盖，保存前先确认。

## 逻辑理解

`逻辑理解` 用于完整条件块之间的逻辑连接，不用于普通检测。

关键规则：

```text
不添加任何逻辑理解行时，平台会把这些思维条件块默认按 AND 组合。
这不是要求每个编排都必须 AND。
共同成立才预警 -> 不加逻辑行
任一完整分支成立就预警 -> 显式添加 逻辑理解 / 或者，并把每个分支展开
```

`逻辑理解 / 或者` 按编程语言 `||` 理解。它分隔的是完整条件块：

```text
A && B && C && !D && !E
||
A && B && F && !D && !E
```

不要写成：

```text
A && B && C
||
F && !D && !E
```

公共前提和公共排除项不会自动跨 OR 继承；每个分支要自己写全。平台行里出现“或者条件”且规则内容为空，含义就是从这里切开上下两个分支。

已知逻辑选项：

```text
或者
前置条件结束
输出分支预警
输出其他预警
预警结果反转
预警内容输出
预警结果数量
预警框内目标数量
预警内容描述
```

已从平台组件列表确认的 `parsingId`：

| 组件 | parsingId |
| --- | --- |
| 或者 | logic_or |
| 前置条件结束 | logic_pre |
| 输出分支预警 | logic_branch |
| 输出其他预警 | logic_else |
| 预警结果反转 | alarm_reverse |
| 预警内容输出 | alarm_ocr |
| 预警结果数量 | alarm_counter |
| 预警框内目标数量 | alarm_inner |
| 预警内容描述 | alarm_msg |

### 逻辑辅助项的使用边界

- `输出分支预警`：多条件调试时用于确认哪一段满足；一旦输出分支预警，按从上到下的执行顺序停止继续向下判断。
- `输出其他预警`：作为前面分支未命中时的兜底结果，通常放在最后，因为执行后不再继续向下判断。
- `预警结果反转`：把最终条件结果反转，适合“不在岗、未出现”等缺失类结果；条件本身能正向描述时，优先用正向理解再反转结果，避免把长反向 prompt 写复杂。
- `预警内容输出`：需要把目标中的文字带入预警或向外部接口推送时，与文字识别/OCR配合使用。
- `预警结果数量`：按预警结果数量设置触发门槛，例如人员聚集需要超过指定人数；不要把它和目标理解里的置信度混淆。
- `预警框内目标数量`：统计预警框内的目标数量，适合只关心指定目标框内部密度的场景。
- `预警内容描述`：在满足预警条件后输出目标描述，通常需要先有多模态目标理解。
- `内容描述`：平台页面存在的描述类选项；具体字段值和编码以当前页面为准，不要自行编造 parsingId。

OR 示例：

```text
思维条件1: 目标理解 / 多模态目标理解 / person / 大于 / 0 / 阈值 50
思维条件2: 内容理解 / 正向思维1 / 图中人员靠近水域、岸边、桥边或河道边等临水危险区域
思维条件3: 内容理解 / 反向思维1 / 图中人员在平地上、护栏内、人行道或非临水区域正常行走
思维条件4: 逻辑理解 / 或者
思维条件5: 目标理解 / 多模态目标理解 / person / 大于 / 0 / 阈值 50
思维条件6: 内容理解 / 正向思维1 / 图中人员跨坐在桥梁栏杆、护栏或边缘上，身体悬空于水体上方或部分探出护栏外
思维条件7: 内容理解 / 反向思维1 / 图中人员在平地上、护栏内、人行道或非临水区域正常行走
```

没有逻辑行时，不要假设每行可以独立触发。

## 全结构化理解

已知组件：

| 组件 | parsingId |
| --- | --- |
| 全结构化理解 | all_struct |
| 全结构化理解-深度 | all_struct_dec |

只在平台已有模板、截图或原配置明确给出时使用；普通算法编排不要主动发明全结构化条件。

格式：

```text
全结构化理解 / 全结构化理解 / [结构化提取要求]
全结构化理解 / 全结构化理解-深度 / [深度结构化提取要求]
```

如果要继续过滤全结构化结果：先编写外挂算法，外挂算法中不要再次牵引全结构化目标；创建应用时选择对应全结构化算法，增加预警条件并挂载该外挂算法。只有平台已有全结构化模板或原配置明确给出时，才走这条路径。

## 执行顺序

整体算法按从上到下的顺序执行，逐层过滤。

只有上面的条件满足后，才会继续执行下面的算法或条件。把便宜、稳定、宽泛的条件放前面，把细节判断、排除项、调优条件放后面。

## 启用区域框

`启用区域框` 表示不使用整个画幅作为检测范围，而是只取画面中的一部分区域进行检测。

涉及固定点位、禁区、设备区域、门口、桶边、道路局部等场景时可以开启；如果业务要求全画面检测，保持关闭或按平台默认。

有明确目标框、需要定位告警对象时开；纯整图分类、不需要框或目标框不稳定时可关。

平台区域编码规则：只有一个区域框时通常不填设备区域编码，绘制区域也不要命名；如果某一思维条件填了区域编码，其他思维条件也要填，整图使用 `full`。离线视频绘制区域前应使用平台生成的流水图片作为设备预览图，绘制后先确认再保存；大场景小目标可配合分屏检测。

## 添加到门户

`添加到门户` 是展示开关，不是检测逻辑。默认不要开；只有用户要求、重点展示类算法或需要门户侧直接查看时再开。

## 解析模式补充

解析模式按任务结构选，不要机械默认通用或深度：

| 模式 | 适合 |
| --- | --- |
| `通用模式` | 简单锚点、普通物体识别、目标关系容易被串行拆散 |
| `深度解析模式` | 整图事件、行为语义、身份服饰、脸部表情、事故状态 |
| `深度串行解析` | 多锚点局部交互、穿戴缺失、手部动作、目标间逐步过滤 |

两个及以上 `目标理解` 不等于必须串行；如果是整图关系或事件，先考虑深度解析或通用模式加关系语义。

深度模式已观察控件：

```text
延伸比例
自定义延伸比例
延伸比例: 0% / 2% / 3% / 5% / 6% / 8%
```

整图 `延伸比例` 以整张图片为基准，`自定义延伸比例` 以目标框为基准。普通整图延伸通常先从 1-5% 试起；只有需要把目标外上下文带入判断时才增大自定义比例，例如“人是否骑车”可能需要向下延伸到车辆区域。框过小会丢掉必要上下文，框过大又会把旁边干扰目标带入。
